## 四、设计实现过程（20分）

### 4.1 设计和实现过程（5分）

上次作业画出了页面和操作流程，这次把它做成了网页。我们先做发布、浏览、搜索、查看详情和修改状态，再补筛选、收藏、个人主页等功能。

比如，一位同学丢了雨伞，可以发布名称、丢失时间、可能丢失的地方和联系方式。另一位同学在首页搜索“雨伞”，打开详情后联系发布者。确认找回以后，由发布者到“我的发布”标记“已找到”。如果是捡到物品，归还后标记“已归还”。其他人重新加载列表或打开详情时，也能看到更新后的状态。

这次实现的是网页。上次原型使用小程序的页面形式，因此保留了“首页、发布、我的”三个入口。当前没有实现原生微信小程序，也没有做站内聊天、地图定位或学校实名认证。联系双方需要根据详情中的联系方式，在应用外沟通。

开发中使用了AI辅助编写代码、整理测试和排查样式问题。下面的功能、代码和测试结果均对应实际项目；两人的协作过程和耗时按真实记录填写。

#### 从原型到页面

我们保留了原型里的主要页面，把它们接成可以操作的流程。首页负责集中展示和搜索；发布页负责收集信息；详情页负责展示完整内容和联系方式；“我的”负责管理本人发布及收藏。

实际做出来以后，页面又经过了几轮调整。首页最初提示文字较多，公告和卡片也偏大，后来缩短了卡片，把外露的筛选收为“寻物、招领、收藏”，其余放进漏斗按钮。丢失和拾取的时间放在卡片上，发布时间放在详情和“我的发布”里。这样找东西时先看到的是事情发生的时间。

界面采用暖棕色表示寻物、浅绿色表示招领，已完成的信息用灰蓝色区分，同时保留文字状态。底部导航在各个页面都可以使用。收藏、弹窗和按钮增加了点击反馈，减少操作后没有反应的感觉。

## 五、附加特点的设计与展示（10分）

### 5.1 特点的目的与意义（3分）

附加功能主要考虑四件事：信息多时怎样缩小范围，时间和地点不确定时怎样表达，操作后怎样知道是否成功，以及怎样方便地回来继续查看。对应增加了多选筛选、模糊范围、收藏、个人主页和一系列界面提示。紧急公告则把需要留意的物品放在首页，突出时间和地点。

这些设计来自开发中的实际讨论和页面修改，下面说明各项的做法与用途。目前还没有通过实际校园使用统计证明找回效率有所提高。

### 5.2 特点的设计实现（3分）

#### 1. 首页先展示有用的信息

顶部栏保留应用名称、学校和个人入口，下面依次是公告、搜索和物品列表。公告与卡片控制高度，减少重复说明，让进入页面的人能尽快看到物品。首页卡片只放标题、简短描述、地点和事件时间；完整描述放在详情中，避免每条信息占很长一页。

#### 2. 快捷筛选与展开筛选

只按物品名称搜索，结果多时仍然不好找。现在可以展开漏斗按钮，选择多个地点和分类，再限定丢失或拾取日期。面板内部可滚动，点击应用后保持展开，方便继续调整。

同组的条件取“或者”，不同组的条件取“并且”。比如选“教学楼、食堂”和“生活用品、电子设备”，结果必须在所选地点之一，同时属于所选分类之一。都不选表示不限制。日期筛选包含起止两天，依据事件发生时间筛选。

首页外露的按钮只有“寻物、招领、收藏”，其他条件放进漏斗按钮。展开后的选项大小统一、文字居中，多选项显示勾选。面板内部滚动，重置和应用按钮保留在底部，防止选项挤占整个页面。修改选项先保留为草稿，点击应用才更新结果；漏斗上的数量提示已经启用的条件，列表同时显示结果数，并提供重置入口。

#### 3. 最近搜索与无结果提示

点击搜索框可查看最近搜索，点历史词可以重新搜索。最多保留八条，重复搜索移到最前面，输入首尾空格会去掉。用户可以在设置中关闭记录或清空历史。

没有匹配信息时，页面明确显示无结果，并给出清除筛选和发布信息的入口。筛选后显示当前结果数量，避免用户分不清是没有相关物品，还是筛选条件太多。

#### 4. 丢失、拾取、发布和修改时间分开

首页和收藏卡片展示丢失或拾取时间，方便按事情发生的时间寻找。详情与“我的发布”另外展示发布时间和修改时间，编辑时保留原发布时间。时间范围筛选也依据丢失或拾取日期。

发布表单只提供“具体时间”和“大致日期”，记不清几点时可以只填日期，不需要编一个时刻。字段旁说明这一点，日期展示也保留相应的准确程度。

#### 5. 不确定地点用模糊范围表达

寻物发布也支持选择多个可能区域，并明确显示“模糊范围”。补充地点写成“最有可能的地点”，避免把不确定的地点说成确定地点。招领仍填写实际拾取区域。时间可以填具体时刻，也可以只填大致日期。

#### 6. 配色、图标和文字一起提示状态

寻物卡片用暖棕色，招领卡片用浅绿色，完成后用灰蓝色。颜色都降低了饱和度，并保留“寻找中、待认领、已找到、已归还”等文字。用户可以通过颜色快速区分，也能直接读出状态。

收藏采用粉色实心爱心，首页收藏筛选使用同一套颜色；选中的卡片也有轻微边框变化。筛选和发布页的勾选标记独立摆放，避免挤偏选项文字。字体大小、行距和文字层级统一，物品名称、状态与时间地点各有清楚的位置。

#### 7. 收藏和复制联系方式

暂时不确定是不是自己的物品时，可以先收藏，再从“我的收藏”回来查看。收藏按钮有颜色和点击反馈。详情提供复制联系方式的入口，减少来回输入；浏览器不允许自动复制时，可以手动复制。

收藏只保存物品编号，避免把整条信息复制一份后变成旧数据。删除发布时，后端会一起清理对应的收藏关系。

点击收藏后，保存成功才更新爱心和数量。取消收藏时恢复空心；在收藏列表里，卡片淡出后移除。短暂的弹跳和光圈会结束，不会一直留在画面上。更新时尽量保留原按钮和列表，避免页面跳动。

#### 8. 我的页面把概况和操作分开

上方显示昵称、头像、简介、校区，以及发布总数、进行中、已完成和收藏数量。下方分成“我的发布”和“我的收藏”，管理操作只放在本人发布里。

“我的发布”增加已完成筛选，可以与寻物或招领组合使用。筛选与数量放在同一区域，避免几个字单独占一行。完成后仍保留原记录；误点完成可以取消，恢复后内容和发布时间不变。

#### 9. 发布者主页和个人设置

详情里的发布者可以打开公开主页，查看简介、校区、发布总数、进行中及已完成数量。这些数据从该用户的发布计算，完成或取消完成后会更新。统计只能作为了解发布记录的参考。

设置中可以修改昵称、头像、简介和校区。校区用福州大学校区选项，减少同一个校区被写成不同名称的情况。常用联系方式只在本人设置中保存，新发布时可以带入；公开主页不展示这项个人设置。

浏览偏好用分段按钮选择默认排序，用开关控制是否记录最近搜索。数据管理显示搜索和收藏数量，没有内容时相应清空按钮不可用，清空收藏前需要确认。设置按个人资料、账号安全、浏览偏好、数据管理和帮助分区，便于找到入口。

#### 10. 图片上传与表单提示

本地后端运行时，物品照片支持点击选择和拖入。选择后展示预览与文件名，可以更换或移除；限制JPG、PNG、WebP格式和5MB大小。选择无效文件时保留已经选好的照片，并提示原因。切换时间准确程度时也保留待上传的图片。

图片和描述标为选填，必填项用星号提示。提交失败时在具体字段旁说明问题，并引导补充，避免只弹出一句“提交失败”。图片没有上传时使用统一默认配图。表单中的名称、地点和描述各给一个简短填写示例，帮助用户写出可辨认的线索。

#### 11. 确认弹窗与操作反馈

标记完成、取消完成、删除和清空收藏等操作先确认。弹窗写清楚操作对象与结果，例如取消归还时说明该物品将恢复为待认领；确认按钮使用“恢复进行中”等具体文字，取消按钮默认获得焦点。关闭后恢复原来的焦点，确认过程中避免重复点击。

短消息区分成功、失败和普通提示，可以手动关闭。复制受浏览器权限限制时给出手动复制办法。提示主要帮助用户决定下一步操作，避免在各个页面重复堆放说明。

#### 12. 底部导航与动效

“首页、发布、我的”导航在各个页面保留，滚动时也能使用，页面底部留出空间，防止遮住提交按钮。针对发布页曾出现的横向溢出，修复隐藏上传控件的尺寸，并在手机与桌面宽度下检查。

按钮、链接和表单控件有一致的按下反馈；支持振动的触屏设备还可提供短振动。收藏、筛选、页面和弹窗使用轻量过渡，筛选应用时保留面板及内部滚动位置，公告保留当前切换位置，减少整页重新生成带来的跳动。用户启用系统“减少动态效果”时，页面会减少动画。

#### 13. 紧急寻物公告

紧急公告展示物品、丢失时间、地点和酬谢金额，支持切换公告并进入对应详情。当前配图及初始内容用于演示，尚未作为真实校园服务运营。

公告支持左右滑动、箭头和圆点切换，同时显示当前位置。每条公告都有对应详情入口。“联系我们发布紧急”提供发布入口：完整本地应用中可以选择本人尚未完成的寻物信息并填写酬谢，提交给管理员审核；直接打开HTML时展示团队联系信息。

#### 14. 账号与演示数据分开管理

完整本地应用支持注册登录、修改个人资料和多账号发布。发布、收藏和个人设置通过接口保存到数据库，图片保存到本地文件，重启后继续保留。服务端检查发布归属，其他账号不能编辑或更新别人的状态。

初始演示账号填有头像、昵称、简介、校区和已有发布，方便测试管理流程。联系方式使用展示内容，已有用户修改不会在每次启动时被覆盖。直接打开HTML的体验与后端数据分开保存，运行方式在使用说明中明确列出。

## 七、单元测试与测试评价（10分）

### 7.1 测试工具与简易教程（4分）

测试使用Mocha，断言使用Node自带的`node:assert/strict`。Mocha负责组织和运行测试，断言负责比较实际结果与预期结果。入门可参考[Mocha官方文档](https://mochajs.org/)。

在已有项目中先执行`npm.cmd ci`安装依赖，再执行`npm.cmd test`。`describe`把相关测试放在一组，`it`写一个具体用例。遇到异步接口测试时使用`async/await`，让测试等到请求结束再判断结果。

### 7.2 测试代码与测试功能（3分）

下面是项目中的收藏测试：

```javascript
const { describe, it } = require('mocha');
const assert = require('node:assert/strict');
const D = require('../js/data.js');

describe('收藏', () => {
  it('favorite toggle adds once then removes', () => {
    const a = D.toggleFavorite([], 'one');
    assert.deepEqual(a, ['one']);
    assert.deepEqual(D.toggleFavorite(a, 'one'), []);
  });
});
```

第一次调用时编号不存在，应该加入；第二次已经存在，应该移除。它检查了收藏函数的两个分支。断言失败时，Mocha会指出失败用例并显示结果差异。需要单独排查收藏时，可执行`npm.cmd test -- --grep "favorite"`。

## 九、代码模块的困难、解决过程与收获（4分）

### 9.1 遇到的问题

图片上传区域调整后，进入发布页时底部导航看起来不见了。最开始从定位入手，试着根据可视区域调整底栏位置，但没有解决根因，反而出现底栏位置变化。

### 9.2 排查与解决过程

后来检查了页面实际宽度，发现一个隐藏的文件输入框被普通表单的`width: 100%`样式覆盖。控件虽然看不见，却把页面撑宽了。浏览器因此重新计算视口，底栏也跟着跑出可见范围。

最后保留底栏的固定定位，为上传区域增加相对定位，并明确限制隐藏控件的尺寸。修复代码节选：

```css
.item-image-editor { position: relative; }
.form-field input.sr-only {
  position: absolute;
  width: 1px;
  height: 1px;
  max-width: 1px;
  min-width: 0;
  padding: 0;
  overflow: hidden;
}
```

测试也跟着修改：横向溢出比较页面的`scrollWidth`和`documentElement.clientWidth`。原先比较`innerWidth`，它也可能随页面撑宽，导致测试漏报。随后把发布页纳入手机宽度检查。

### 9.3 收获与改进

这个问题让我们认识到，看起来是底栏的问题，也可能由页面里一个看不见的控件引起。以后先测量布局，再改定位；发现一个漏测场景，就把它补进测试。

程序已经能走完“发布—浏览或搜索—详情—联系—更新状态”。这次反复修改的地方主要是信息摆放、筛选交互、图片和底部导航。原型能点通以后，实际页面仍需要用真实输入、不同屏幕宽度和错误情况检查。

下一步更需要让同学拿实际场景试用，看看名称、地点和时间是否够用，以及找到以后是否容易发现状态更新入口，再决定继续加什么功能。
