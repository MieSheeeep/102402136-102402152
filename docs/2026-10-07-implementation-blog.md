## 四、解题思路描述与设计实现说明（20分）

### 4.1 解题思路：先把查找和归还串起来

这个问题的核心是让失主和拾得者看到同一批信息。我们把寻物与招领放进统一列表，用类型字段区分，再围绕发布、查找、联系和更新状态组织页面。用户先在列表中判断物品是否相关，打开详情核对特征，在应用外联系，最后由发布者标记找到或归还。

设计时先确定一条物品记录，再确定哪些页面读取它。首页显示摘要，详情展示完整内容，“我的发布”提供管理操作，收藏只保留物品编号。这样名称、地点或状态修改后，几个入口不会各自保存不同的内容。

实现上的另一个选择是把业务规则从页面中提出来。名称是否为空、多个区域怎样匹配、完成后显示什么文字，都由`data.js`处理；页面只负责收集输入和展示结果。直接打开HTML时保存到浏览器，启动后端时保存到数据库，两种入口使用相同的校验和状态规则。

下面的流程图把网页操作和应用外联系分开。系统保存线索、提供查找与联系方式，发布者确认物品找回以后，再更新完成状态。

### 4.2 整体结构：页面、规则与存储分开

前端使用HTML、CSS和JavaScript，后端使用Fastify，数据保存到SQLite，图片保存为文件。直接打开HTML时，页面使用浏览器存储；启动本地后端时，同一套页面通过接口访问共享数据。

<img src="blog-images/2026-10-07/data-flow.png" alt="两种运行方式下的前端、接口与存储结构" width="680">

`index.html`提供顶部栏、主内容区、底部导航和弹窗容器。`app.js`读取地址中的`#home`、`#publish`、`#detail/编号`等路径，选择对应页面；`views.js`根据数据生成页面内容。详情按物品编号找到记录，编辑页回填该记录，“我的发布”按当前用户编号筛选。

页面重新生成后，原来的按钮元素也会被替换，因此按钮操作统一在主容器上监听。点击时读取按钮的`data-action`，例如收藏、应用筛选或确认完成，再交给对应函数处理。底部导航放在主内容区之外，重绘页面不会把它一起替换。

| 文件 | 具体职责 |
| --- | --- |
| `js/app.js` | 路由、事件监听、表单草稿、弹窗、页面状态与刷新 |
| `js/views.js` | 卡片、详情、表单等页面模板，用户文字转义和关键词高亮 |
| `js/data.js` | 输入校验、创建与更新记录、搜索筛选、收藏和状态规则 |
| `js/api.js` | 请求接口、处理响应错误、上传图片和携带登录凭据 |
| `server/app.cjs` | 登录会话、接口校验、权限判断、数据库与图片读写 |

首页和个人页切换时先显示已有数据，再向后端获取更新，减少“正在加载”的闪动。刷新请求带有顺序标记，较早发出但较晚返回的响应不能覆盖较新的结果。窗口重新获得焦点时也会刷新相关页面。

<img src="blog-images/2026-10-07/01-overview.png" alt="首页、发布与我的页面" width="760">

注册和登录由后端处理，密码使用加盐哈希保存，登录成功建立会话。浏览器通过HttpOnly Cookie携带会话，写操作同时检查CSRF凭据；服务器依会话确定用户，不能只相信页面传来的用户编号。游客可浏览，发布、收藏和查看联系方式需要登录。

### 4.3 数据组织：一条物品记录连接多个页面

每条物品记录包含物品编号、发布者编号、类型、名称、分类、地点、事件时间、联系方式、描述、图片、状态和版本。首页、详情、我的发布和收藏读取同一条记录，修改一次后各处使用更新后的内容。

下面用一条寻物信息说明静态模式保存的JSON结构。字段与`data.js`一致，内容用于说明数据关系：

```json
{
  "version": 1,
  "items": [
    {
      "id": "post-demo-umbrella",
      "ownerId": "me",
      "type": "lost",
      "name": "黑色长柄雨伞",
      "category": "生活用品",
      "locationGroups": ["教学楼", "图书馆"],
      "locationGroup": "教学楼",
      "locationDetail": "教学楼A区302附近",
      "occurredAt": "2026-10-08T08:20",
      "timePrecision": "datetime",
      "contact": "微信：campus_demo",
      "description": "伞柄有一圈银色金属环",
      "image": "assets/default-item.svg",
      "status": "open",
      "createdAt": "2026-10-08T01:00:00.000Z",
      "updatedAt": "2026-10-08T01:00:00.000Z"
    }
  ],
  "favorites": ["post-demo-umbrella"],
  "recentSearches": ["黑色 雨伞"],
  "preferences": { "sort": "newest", "saveSearchHistory": true }
}
```

`items`保存物品内容，`favorites`只保存物品编号。这样收藏后的物品被修改时，收藏列表仍读取同一条最新记录。`locationGroups`保存多个可能区域，`locationGroup`保留第一个区域用于兼容单区域字段；前者用于模糊范围匹配。最外层的`version: 1`是本地存储格式版本，与后端每条发布用于冲突检查的版本号不同。

在后端中，`items`表将`id`、`owner_id`和记录JSON分开保存，另外有递增的`version`列。用户资料与收藏关系单独建表，读取时再组合成页面需要的数据。物品照片保存文件，记录中的`image`引用地址，避免把照片本身塞进每条数据库记录。

丢失／拾取时间用`occurredAt`保存，`timePrecision`区分具体时间和大致日期；`createdAt`记录发布时间，`updatedAt`记录修改时间。寻物可以填写多个可能区域，展示时标注“模糊范围”，补充位置写为“最有可能的地点”；招领填写一个拾取区域和具体拾取地点。

发布记录通过`ownerId`关联用户。详情读取发布者最新昵称和头像，公开主页读取允许公开的简介、校区及该用户发布列表，计算发布总数、进行中和已完成数量；私人收藏和常用联系方式不公开。个人资料修改写入用户表，所以历史发布不用逐条改昵称。

SQLite保存用户、会话、物品、收藏、偏好与公告，上传目录保存图片。首次初始化写入演示账号、七条物品和三条公告，初始化标记防止重启覆盖用户修改。直接打开HTML时使用独立的浏览器存储，两种方式不会自动互相导入。公告关联进行中的寻物记录，读取时排除到期或已完成内容，点击打开对应物品详情。

| 数据表 | 保存内容 | 与其他数据的联系 |
| --- | --- | --- |
| `users`、`sessions` | 账号资料、密码及恢复码摘要、偏好、会话 | 会话关联用户；发布、收藏、图片以用户编号确定归属 |
| `items` | 物品编号、发布者编号、内容、版本 | 发布者资料从用户表读取；完成数量从物品状态统计 |
| `favorites` | 用户编号、物品编号 | 两个编号组成唯一关系；删除物品后级联删除 |
| `uploads`与图片目录 | 图片编号、所属用户、大小和文件 | 物品及头像引用图片地址 |
| `urgent_requests`、`notices` | 申请或公告所关联物品、酬谢；公告另存到期时间 | 关联原发布；审核批准时写公告并删除申请 |
| `app_meta` | 演示初始化及资料迁移标记 | 防止重启时重复导入、覆盖已经修改的数据 |

### 4.4 发布与保存：从表单输入到一条记录

提交表单时，`app.js`先读取输入，调用`validateItem()`检查必填内容、长度、分类、区域和日期。只有空格的名称不通过校验。错误放到对应字段旁，输入保留，并将焦点移到第一个错误字段。校验通过后用`submitting`和禁用按钮防止重复提交。

后端模式下，有图片时先调用`POST /api/uploads`取得图片地址，再将表单发送到`POST /api/items`。服务器再次校验，并从登录会话取得发布者编号，创建记录后写入SQLite。前端收到成功响应后重新读取状态，进入发布成功页；请求失败则提示原因并保留表单。这样成功提示对应已经保存的数据。

`app.js`中后端提交分支的核心代码如下，省略了清空草稿和错误提示部分：

```javascript
requireLogin();
if (pendingItemFile) draft.image = await API.upload(pendingItemFile);
const edit = currentRoute.page === 'edit';
const record = await API.request(
  edit ? 'PATCH' : 'POST',
  edit ? `/items/${encodeURIComponent(currentRoute.id)}` : '/items',
  {
    ...draft,
    ...(edit ? {
      version: state.items.find(post => post.id === currentRoute.id)?.version
    } : {})
  }
);
await refreshRemote(false);
navigate(edit ? 'my' : `success/${encodeURIComponent(record.id)}`);
```

几个`await`按依赖顺序执行：先取得图片地址，再保存物品，最后刷新页面数据。`API.request()`统一补上`/api`前缀，将普通对象序列化为JSON，并把非成功响应转为错误；表单处理的`catch`负责展示错误，`finally`恢复提交按钮。

静态模式下，`createItem()`生成新记录，`createStore()`把状态写入`localStorage`。图片在浏览器中用Canvas缩小到长边不超过720像素，转为WebP数据地址后随记录保存；后端模式则保存图片文件，记录只引用返回的地址。选择文件支持预览、更换、移除和拖入，没有照片时使用默认配图。

浏览器存储只能保存字符串，所以写入前使用`JSON.stringify()`，读取后使用`JSON.parse()`。`createStore()`还会校验结构，并比较当前存储内容与上次读取的内容；如果另一个标签页已经修改数据，就拒绝用旧状态覆盖。下面是保存分支的节选：

```javascript
if (expectedRaw === undefined || currentRaw !== expectedRaw) {
  throw new Error('另一页面已更新数据，请刷新当前页面后重试；本次修改未保存。');
}
const serialized = JSON.stringify(state);
storage.setItem(key, serialized);
expectedRaw = serialized;
```

这里的比较检查用于发现多标签页之间的旧数据覆盖，不能替代后端数据库的条件更新。实际方法还处理了存储被禁用、容量不足和数据格式无效等错误。

### 4.5 搜索与列表：先匹配，再分批展示

首页从`/api/state`读取物品集合，调用`queryItems()`计算结果。关键词按半角或全角空白拆开，忽略大小写，每个词都要在名称、描述或具体地点中命中。例如“黑色 雨伞”要求两个词都匹配，纯空白不限制结果。

关键词判断在`data.js`中单独写成函数，列表筛选调用它，高亮也使用相同的拆词结果：

```javascript
function splitKeywords(value) {
  return text(value).toLocaleLowerCase().split(/[\s\u3000]+/).filter(Boolean);
}

function matchesKeywords(item, words) {
  if (!words.length) return true;
  const haystack = [item.name, item.description, item.locationDetail]
    .map(text).join('\n').toLocaleLowerCase();
  return words.every(word => haystack.includes(word));
}
```

`every()`表示每个关键词都要出现，但可以出现在不同字段。例如“雨伞”出现在名称，“金属环”出现在描述，也能匹配同一条记录。

地点和分类多选采用组内任选、组间同时满足：选教学楼与食堂，两处都可以；再选生活用品，就还要满足分类。日期范围依据丢失／拾取日期，包含开始和结束日期；最新或最早排序依据发布时间，两种时间分别处理。

展开面板后的修改保存在`filterDraft`，应用时才替换正在使用的条件。关闭未应用的面板时丢弃草稿，应用后保持展开。筛选内容单独滚动，重置和应用按钮保留在面板底部。

结果先筛选、排序，再通过`paginate()`按12条分批显示。点击加载更多增加展示数量；关键词、类型、日期等条件变化时，通过条件签名将数量重置为12。没有任何发布和有发布但没有匹配，分别显示不同提示。卡片与详情使用同一套关键词拆分结果，高亮时逐段转义用户文字，再加入程序生成的`mark`标签。

### 4.6 编辑与状态同步：归属检查和版本检查

编辑复用发布表单，通过`PATCH /api/items/:id`提交内容和原版本号。服务器检查当前账号是否为发布者，再比较`version`。版本过旧返回409，提示刷新后再操作，避免旧页面覆盖新修改。编辑保留物品编号、发布者、原类型和发布时间，只更新可修改内容、修改时间与版本。

完成与取消完成修改同一个`status`字段：`open`表示进行中，`completed`表示完成。`statusLabel()`结合类型生成“寻找中／已找到”或“待认领／已归还”。页面用同一状态选择卡片颜色，个人页统计也从物品状态计算。完成、取消完成和删除先打开确认弹窗，取消时不写入数据。

下面是`server/app.cjs`中更新接口的节选：

```javascript
const user = auth(req);
const old = getItem(req.params.id, user);
const body = req.body || {};
if (old.ownerId !== user.id) fail(403, '只能管理本人发布的信息');
if (body.version !== old.version) fail(409, '信息已被修改，请刷新后重试');
let item;
if (body.status !== undefined) {
  if (!['open', 'completed'].includes(body.status)) fail(400, '状态不正确');
  item = (body.status === 'completed' ? D.completeItem : D.reopenItem)
    ([old], old.id, user.id)[0];
}
```

第一步从登录信息确定用户，再检查这条发布属于谁。因此，其他人即使直接调用接口，也不能修改别人的信息。`version`用于检查页面中的信息是否已经过时，避免旧页面覆盖新的修改。最后根据请求选择完成或取消完成。

写入数据库时，再把版本条件放进更新语句。下面是同一接口保存记录的代码：

```javascript
const result = db.prepare(
  'UPDATE items SET data=?,version=version+1 WHERE id=? AND version=?'
).run(JSON.stringify(item), old.id, old.version);
if (!result.changes) fail(409, '信息已被修改，请刷新后重试');
return getItem(old.id, user);
```

例如，同时打开两个页面修改同一条信息：第一页提交后版本加一，第二页的旧版本更新不到记录，接口返回409并提示刷新。正常更新则返回数据库中的新记录，再更新页面。这个检查既放在读取后，也放在实际写入时，防止检查与保存之间发生其他修改。

状态函数只修改状态和修改时间，保留名称、地点、事件时间及原发布时间。接口测试分别验证了他人修改被拒绝、旧版本提交被拒绝，以及完成与取消完成后统计变化。

`js/data.js`负责把内部状态翻译成界面文字：寻物完成显示“已找到”，招领完成显示“已归还”。这使不同页面不必各自猜状态。

例如一条招领信息归还后，列表显示“已归还”，个人页的完成数量相应变化。取消完成恢复为待认领，物品描述、事件时间和发布时间保持原样。完成、取消完成和删除都先确认，再保存结果。

### 5.1 收藏：把可能相关的线索留下来

首页卡片和详情都有收藏入口，点爱心就能保存，在首页“收藏”筛选或“我的收藏”中再次查看。用户不必马上决定是不是自己的物品，也可以先留着，之后补充线索或联系发布者。

```javascript
function toggleFavorite(favorites, id) {
  return favorites.includes(id)
    ? favorites.filter(value => value !== id)
    : [...favorites, id];
}
```

### 7.2 日期筛选：从规则推到测试数据

日期筛选的规则是“按丢失／拾取日期判断，并包含起止两天”。测试不能只放一条落在中间的记录，否则即使漏掉开始或结束日期，也可能通过。

我们先准备一条其他字段都合法的物品，再用`item(overrides)`只覆盖这次要检查的字段。下面是`tests/data.test.cjs`中辅助函数和日期用例的整理节选：

```javascript
const now = '2026-10-06T10:00:00.000Z';
const input = {
  type: 'lost', name: '黑色雨伞', category: '生活用品',
  locationGroup: '教学楼', locationDetail: 'A区302',
  occurredAt: '2026-10-06T09:20', contact: '微信：demo',
  description: '银色金属环'
};
function item(overrides = {}) {
  return {
    id: 'one', ownerId: 'me', ...input, status: 'open',
    createdAt: now, updatedAt: now, ...overrides
  };
}

it('event date range includes both ends and uses the event date', () => {
  const list = [
    item({ id: 'first', occurredAt: '2026-10-01', timePrecision: 'date' }),
    item({ id: 'last', occurredAt: '2026-10-06T23:59' }),
    item({ id: 'old', occurredAt: '2026-09-30T12:00' }),
    item({ id: 'unknown', occurredAt: '', timePrecision: 'unknown' })
  ];
  const ids = D.queryItems(list, {
    timeRange: 'custom', dateStart: '2026-10-01', dateEnd: '2026-10-06'
  }).map(x => x.id);
  assert.deepEqual(ids, ['first', 'last']);
  assert.equal(D.queryItems(list, { timeRange: 'all' }).length, 4);
});
```

四条记录的发布时间相同，事件时间分别在起点、终点23:59、范围外和缺失状态。预期只留下前两条，既检查两端是否包含，也检查筛选是否误用了发布时间。缺少事件时间的旧记录不能匹配指定范围，但选择全部时间时仍能看到。

固定时间还有一个好处：今天运行与明天运行得到同样结果。比较编号数组而不是整条记录，则把断言集中在“筛选留下了谁”，不会因其他字段变化干扰判断。

### 7.3 怎样考虑正常、错误和容易被漏掉的情况

构造数据时先写清规则，再找规则中的分支和边界。这是本项目采用的白盒思路：看到代码中的类型判断、空数组判断、日期比较和权限判断后，分别准备能进入不同分支的输入。每组数据尽量只改变与当前规则有关的字段。

| 检查方向 | 为什么这样构造 | 数据与预期 |
| --- | --- | --- |
| 必填输入 | 看起来填了内容，去掉空白后却可能为空 | 名称全为空格、联系方式为换行，预期指出字段错误 |
| 搜索组合 | 单个词能命中，不代表多个词的关系正确 | 名称有“雨伞”、描述有“金属环”，两个词同时命中；不存在的词排除记录；兼容大小写和全角空格 |
| 多选条件 | 防止把组内任选写成全部满足，或忽略组间组合 | 四条不同地点、分类记录，地点组取并集，再与分类组取交集 |
| 展示数量 | 正常第一页之外还可能有空集合和异常限制 | 30条记录限制12／24条，检查剩余数量；空集合、负数和小数检查处理规则 |
| 文本显示 | 正常中文无法发现转义错误 | 输入带标签、引号、事件属性和正则字符的文字，预期显示文字并保留正确高亮 |
| 状态修改 | 同一完成状态在寻物和招领上有不同文案 | 分别构造两种类型，取消完成后状态恢复，内容与发布时间保留 |
| 图片 | 扩展名和真实内容可能不一致 | 文件名为PNG但内容是SVG，预期拒绝；有效PNG返回WebP；本地图片保存后仍可读取 |
| 账号权限 | 只用本人账号看不到越权问题 | A发布、B修改和删除，预期403；B收藏不改变A的收藏 |
| 旧数据覆盖 | 同一个账号也可能同时开两个页面 | 完成后拿旧版本取消完成，预期409；新版本可以成功 |
| 持久化与关联 | 页面上暂时显示成功，不等于重启后还在 | 重启后读取发布和收藏；删除物品后关联收藏清除 |

## 九、代码模块异常或结对困难及解决方法（4分）

### 9.1 发布页的底栏为什么消失

图片上传区域调整后，进入发布页时底部导航看起来不见了。最开始从定位入手，试着根据可视区域调整底栏位置，但没有解决根因，反而出现底栏位置变化。

### 9.2 从定位问题查到隐藏控件

后来检查了页面实际宽度，发现一个隐藏的文件输入框被普通表单的`width: 100%`样式覆盖。控件虽然看不见，却把页面撑宽了。浏览器因此重新计算视口，底栏也跟着跑出可见范围。

最后保留底栏的固定定位，为上传区域增加相对定位，并明确限制隐藏控件的尺寸。修复代码节选：

```css
.item-image-editor { position: relative; }
.form-field input.sr-only {
  position: absolute;
  width: 1px;
  height: 1px;
  max-width: 1px;
  min-width: 0;
  padding: 0;
  overflow: hidden;
}
```

测试也跟着修改：横向溢出比较页面的`scrollWidth`和`documentElement.clientWidth`。原先比较`innerWidth`，它也可能随页面撑宽，导致测试漏报。随后把发布页纳入手机宽度检查。

### 9.3 验证结果与收获

修复后检查390像素和1200像素宽度下的发布页，确认页面没有横向溢出，进入页面、滚动和操作表单时底栏都能显示。10月9日运行的7项Chrome页面测试全部通过，其中包含发布页布局检查。

这个问题让我们认识到，看起来是底栏的问题，也可能由页面里一个看不见的控件引起。以后先测量布局，再改定位；发现一个漏测场景，就把它补进测试。
